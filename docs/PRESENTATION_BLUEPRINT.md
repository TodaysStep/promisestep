# PromiseStep — presentation blueprint

**Purpose:** Give a new visitor one coherent experience, not a collection of separate initiatives. Retain the established site and its art. This is a research-backed organization of the existing authored work, **not a new product or a deployed page**.

## Narrative spine

**Promise → method → something you can try → safeguards → places to learn → return.**

The opening thought is **“Build software that keeps promises.”** The next reading is the approved working method, exactly **“Refactoring for Kindness, Familiarity, and Visual Metaphor.”** Kindness respects people; familiarity builds on what people already know; visual metaphor makes ideas understandable. Distinguish them visually and semantically rather than collapsing them into interchangeable icons.

The first screen should carry one clear thought and two meaningful paths, not every feature. On mobile, the principal action must remain visible without a large scroll. The image supports the idea; it must not become the only way to read it.

## A working example should carry the proof

The developer experience follows one visible record through **original → reasoned correction → scoped refusal → explicit outcome → canonical export → pause/restore → return**. Preserve the original beside the correction and make unknowns visible. A refusal should be treated as useful evidence of a boundary, never as a broken demo. Do not imply owner-service authorization or independent verification where neither exists.

Use the *actual* package and browser lab; do not create a visually separate imitation that merely looks interactive.

## Product connections, not feature inflation

The lead API direction is **Practical Possibilities and Support for Independent Work at the Center for the Dream**. Software Quality Assurance, Song Dev, Nurture tutorials and Small Step School are related learning paths, not equal-status releases. Put explicit “working / proposed / educational” language next to the relevant capability, in readable text. The HSG I–V material is ratified source material; later volumes are planned.

## Hierarchy & craft

1. **Reading:** one strong serif statement, compact uppercase eyebrow, generous whitespace, restrained body measure.
2. **Seeing:** preserve the 16 original text-free photographic scenes, authored SVG mark and distinct instrument objects; no outside stock or campaign artwork.
3. **Doing:** consistent Download / Run / Inspect / Return labels, immediate state and errors, keyboard access, low-friction mobile navigation.
4. **Understanding:** progressive disclosure for API boundaries and release states; never overwhelm the first screen with a compliance inventory.
5. **Returning:** meaningful back links, archive continuity, and explanation of what was preserved after interruption.

The current source has a 16-scene carousel; do not auto-insert the November 15 campaign artwork. Keep captions and controls outside the art. A final visual acceptance must use the actual hosted website and physical Safari; offline rendered screenshots are rehearsal only.

## Acceptance reading

A first-time visitor should be able to say **what PromiseStep is, what is working today, what it does not authorize, what to try first, and how to return**. A developer should be able to download verified bytes, execute a package example, understand a refusal, correct without erasure, preserve an archive, and compare evidence with claims. A returning visitor should recognize the same visual language across the site, developer hub, learning pages and public reference docs.

This blueprint is prepared for review. It does not declare the current site deployed, reviewed or complete.
